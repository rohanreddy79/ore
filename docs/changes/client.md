# Workstation client: working without git

Branch `rohan/practical-maxwell-cc831e`. No migration. Implements ADR 0016 §2: the `ore` binary is the workstation client, and a developer works on a repository with no git on the machine. Owns `internal/workspace/` (new) and `cmd/ore/workspace.go` (new); additive edits to `internal/gitx/gitx.go`, `internal/pipelines/pipelines.go`, `internal/web/web.go` (one new file, `internal/web/client_routes.go`) and `cmd/ore/main.go` (the command switch, the usage text, and the token lookup of the existing CLI, which now also reads the credentials file).

## What landed

### Server

| Endpoint | What |
|---|---|
| `GET /api/v0/repos/{org}/{name}/archive?ref=&path=…&all=1` | Streams a tar of the tree at `ref` (default: the default branch). With no `path` and no `all` it sends the **active area**: the `paths:` the pipeline file declares at that commit plus the file itself (`pipelines.SparsePaths`, the same rule pipelines and agent workspaces use), or the whole tree when it declares none. Headers: `X-Ore-Commit` (the resolved commit), `X-Ore-Archive-Paths` (a JSON array; `[]` for the whole tree). A failure before the first byte is a normal error status (404 for a bad ref or a path that matches nothing, 400 for a path with `..` or a leading `-`); a failure after it is reported in the `X-Ore-Archive-Error` trailer, since the status is gone. |
| `GET /api/v0/repos/{org}/{name}/diff?from=&to=&path=…` | `{from, to, merge_base, files: [{status, path, old_mode, mode, old_oid, oid}]}` from `git diff-tree -r --raw --no-renames`: A, M (content or mode), D, T. Cached per (repository, from, to, paths), like the other per-commit reads. |
| `POST /api/v0/repos/{org}/{name}/commits` (existing) | Three optional fields. `base`: a new branch starts at this commit instead of the default branch's tip; an existing branch must still be at it, else 409 `{"error": "branch moved: …", "tip": …}` (compare-and-swap for the client). `merge`: the commit becomes a merge of that commit into the branch: tree = server-side `merge-tree` of the tip and `merge`, with `files` applied on top as resolutions; a conflict no file resolves is 409 `{"error", "conflicts", "unresolved", "tip", "merge"}` and nothing is written; a `merge` already contained is 409 "nothing to merge". `files[].encoding: "base64"` carries content that is not valid UTF-8. The answer gains `parent`. |

`gitx` gains `ArchiveTo` (a tar into an `io.Writer`), `DiffTree` (raw name-status with modes and blob ids), `CommitTreeEdits` (edits on any tree-ish with explicit parents; `CommitFiles` now calls it) and `IsOID`. `pipelines.SparsePaths` is the exported form of the sparse rule `execute` already applied.

### Client (`internal/workspace`, `cmd/ore/workspace.go`)

| Command | What |
|---|---|
| `ore login URL [--token T]` | Validates the token (`/api/v0/identity/me`, or `/api/v0/orgs` on a server without identity), records it with the user's name in `~/.config/ore/credentials` (0600 in a 0700 directory; `$XDG_CONFIG_HOME` and `ORE_CONFIG_DIR` are honoured). The token comes from `--token`, `ORE_TOKEN`, or a line on stdin (a prompt on a terminal says the input is visible). Every command resolves the token as `ORE_TOKEN`, then the credentials file for the workspace's server, then the data directory's token for a server on the same machine. |
| `ore open ORG/REPO [DIR] [--all] [--url U]` | Fetches the repository, streams the archive into `DIR` (default: the repository name; must be absent or empty), hashing every file while it is written, writes `.ore/workspace.json`: server, org, repo, default branch, `base` (the commit the manifest describes), `paths` (empty for the whole tree), `user`, the manifest (path → SHA-256, mode, size, mtime). Symlinks are materialized as symlinks (mode `120000`, the hash covers the target); executable files keep their bit. The user name comes from the identity extension when present, else `ORE_USER`, else the operating-system user. |
| `ore save -m MSG` | Flushes the offline queue, refuses while a conflict from the last sync is unresolved, scans the tree (files whose size and mtime match the manifest keep their hash, so a scan of a large tree is a directory walk), diffs it against the manifest (`.oreignore`: blank lines and comments, `*`/`?`/`[]` within a segment, `**` across segments, a trailing `/` for directories, a leading `/` to anchor, `!` to re-include; the workspace's own `.ore/workspace.json` and `.ore/pending.json` are always skipped, the repository's `.ore/pipeline.yaml` never is), loads the content (base64 when not UTF-8), and posts one commit. The first save creates the branch `ore/<user>/<slug-of-the-title>-<6 hex>` at the workspace's `base` (so the change's merge base is where the tree was opened, whatever happened on the default branch since) and opens the change with the message's first line as the title and the rest as the body; later saves append to it with the base as a compare-and-swap. The user sees `saved change #12, patch set 3 (abc12345): 2 changed, 1 added`; the branch name never appears. The manifest moves to the saved state. A merged change makes the next save start a new change from the landed state; a closed change asks for a sync first. |
| `ore sync [--inline]` | Flushes the queue (a sync needs the server, so a queue that cannot be sent stops it). With an open change: if the branch moved without us (another client, the web app's Apply fix), the diff from `base` to the branch tip is applied to the tree first; then, if the default branch has commits the change does not contain (the diff endpoint's merge base says), the server merges the default branch into the change (`merge` on the commits endpoint, message "Sync with main"); on success the diff from `base` to the merge commit is applied to the tree and the merge is read as a patch set; on conflicts the client applies upstream's changes since the merge base where neither the change nor a local edit touched the path, reproduces the server's clean three-way merges for paths both sides changed without overlap, writes the rest as conflicts, and records `pending_merge` so the next save creates the merge commit with the working tree's resolutions (every conflicted path is sent, including "keep mine"). Without a change: the diff from `base` to the tip is applied. Applying a diff: a path not edited locally is written or deleted (modes and symlinks included; empty directories are pruned); a path edited locally and changed upstream is a **conflict**: the local file stays, the upstream version is written as `<path>.upstream` (ignored by saves), and the manifest takes the upstream entry so the local file is the edit the next save records; with `--inline` the two versions are merged line by line against their common base (`Merge3`, a diff3 over Myers matchings), cleanly when the changed regions do not overlap, with `<<<<<<< local` / `=======` / `>>>>>>> main` markers where they do; binary files are never merged inline. Deleted upstream and edited here: the local file stays as an addition. Deleted here and changed upstream: the upstream version is written as `.upstream`. Conflicts outside the materialized area (sparse workspaces) are reported as unresolvable here. |
| `ore land` | Flushes the queue, warns about unsaved edits, refuses without a change, and posts `/changes/{n}/land` with the strategy the level implies (`StrategyForLevel`: below L3 `queue`, L3 `land_when_green`, L4+ `optimistic`), explaining it first. Outcomes: `landed` (merge commit, the verification run when there was one), `blocked` (the policy's reason, a conflict, a red verification), `reverted` (an optimistic landing whose verification failed; the issue number), `queued` (a landing still in progress). On a server without review v1 the v0 `/merge` endpoint is used. The exit status is 0 only for `landed` or `queued`. |
| `ore status` | The repository and its level with the strategy `ore land` would use; the change with its state, title and head, its patch sets, the pipeline runs on the change, the deployments of its head or merge commit; the local edits (first 20 listed); the offline queue; unresolved conflicts; a pending merge; whether the default branch moved (how many files changed in the area). A server that cannot be reached leaves the local part. |

Offline queue (`.ore/pending.json`): a save whose commit request fails with a transport error (or a 502/503/504) is stored as a complete request, in order, and the manifest moves forward as if it had been sent, so later edits diff against the queued content. The first queued save of a new branch carries `base`; later ones build on whatever the previous queued commit produced (no compare-and-swap, so a save another client made to the same change in the meantime is overwritten path by path, both commits staying on the ledger). The queue is sent by the next save, sync or land; the first failure stops the flush and keeps the rest; the change opens after the first queued commit lands. If the change was merged while saves were queued, they start a new change; if it was closed, the user is asked to sync first.

## Edge cases and limits

- The `.ore/` directory is shared: the repository's `.ore/pipeline.yaml` is content, the workspace's `workspace.json` and `pending.json` are not. A repository that itself holds a `.ore/workspace.json` cannot be worked on with this client.
- `.oreignore` is read at the root only; nested ignore files are not supported. Ignored files that already exist in the manifest (materialized by `open`, later ignored) show up as deleted at the next save; delete them from the repository or drop the rule.
- Sparse workspaces: a save can add files anywhere under the directory, including outside the declared paths; a sync only brings upstream changes within the declared paths; a conflict outside them (reported by the server merge) cannot be resolved without `--all`.
- A conflict is file-level by default, as specified: any file edited locally and changed upstream is reported, even when the edits would merge cleanly; `--inline` is where the three-way merge happens. The inline merge is the client's own algorithm; for paths the server merged cleanly during a conflicted sync the client reproduces the merge and what it writes is what the next save records, so what the user sees is what lands.
- Resolving a side-by-side conflict means editing the file and deleting the `.upstream` copy; resolving an inline one means removing the markers. Keeping one's own version untouched is a valid resolution and is sent to the server as such.
- The merge of the default branch into a change is a commit on the hidden branch with two parents, so the change's diff and patch sets stay about the change; review v1 records it as a patch set when the sync reads the patch sets. A server without review v1 lands with the v0 merge and shows no patch sets.
- The offline queue carries no compare-and-swap after its first entry (see above); `ore status` warns while saves are queued. A queued save whose change was merged meanwhile opens a new change.
- Binary files: hashed and saved (base64 over the API), never merged inline; a conflict on one is always side by side.
- Symlinks are materialized as symlinks and saved with mode `120000`. Sockets and devices in the working directory are ignored. Mode changes are only the executable bit, as in git.
- Large files: content travels inside the JSON commit request, which the server caps at 64 MiB per request; a save larger than that fails and should be split.
- `ore land` is synchronous: at L3 it waits for the verification run; at L4 the request returns after the merge and the post-merge verification (the server runs it detached from the request, so an interrupted client cannot cause a spurious revert).
- The commands never run git; the client depends on `internal/gitx` only for the `DiffEntry` type.
