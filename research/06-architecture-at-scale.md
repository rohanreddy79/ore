## 1. Git storage at scale

**GitHub Spokes (ex-DGit, 2016).** 3 full replicas of every repo on separate file servers, kept in sync at the Git-protocol level (not block-level); writes stream synchronously to all 3 and commit only when ≥2 confirm; reads served from the best replica; auto re-replication when a server dies (https://github.blog/engineering/architecture-optimization/introducing-dgit/, https://github.blog/engineering/infrastructure/building-resilience-in-spokes/). Cursor's 2026 post characterizes Spokes as 3PC across replicas with a routing DB tracking every repo's location/checksums, "rough to operate at scale," push throughput falling as replicas increase (https://cursor.com/blog/git-at-any-scale).

**GitLab Gitaly + Praefect, and the Raft direction.** Praefect = virtual storage; reads spread across nodes, writes broadcast to replicas; GitLab recommends Cluster above ~2,000 daily-writing users; Gitaly requires local SSD, explicitly no NFS/cloud filesystems (https://docs.gitlab.com/administration/gitaly/). The Raft epic (#8903) goals: fix Cluster inconsistency, **remove Praefect, remove Postgres, make every Gitaly "a cluster of one"**; each repo gets a WAL replicated by Raft (one Raft group per repo). Last public update 2024-06-18: transactions on staging, Raft PoC started; no 2025–26 GA I could find (https://gitlab.com/groups/gitlab-org/-/epics/8903, https://gitlab.com/groups/gitlab-org/-/work_items/8175 — notes GitLab.com has >75 file servers and most repos have replication factor 1). Gitaly on Kubernetes went GA with GitLab 18.11 (May 7 2026) but Praefect still doesn't support K8s; HA "on the horizon" (https://about.gitlab.com/blog/gitaly-on-kubernetes-generally-available/).

**The 2026 GitLab object-storage design (Git Merge 2026, Patrick Steinhardt).** Repos stored as packfiles + reftables in object storage; an immutable **manifest** lists active packs/reftables; a **generation** = sequence of manifests; manifests are the only mutable thing; Gitaly nodes become stateless local caches; any node serves any repo via routing; MVCC: readers pin a manifest, writers stage immutable artifacts then atomically publish a new manifest; conflicting ref updates = 3-way merge of base/old/new manifests, same-ref pushes conflict. Being upstreamed via Git's pluggable ODB: `object_database` abstraction (2.51), streaming (2.52), packed source (2.53), `odb_source` vtable (2.54), in-memory source + transactions (2.55), maintenance/fsck pluggable (2.56), alternates folded into files backend (2.57, planned). Demos showed a SQLite backend (`.git/git.db`) and an S3 backend (SeaweedFS) (https://gist.github.com/dscho/9c70e07ee54616bbf401b4e5f40969bf).

**Git-on-object-storage, 2026 state of the art (four designs):**
- *Cursor "Continuity"* (Aug 18 2026): S3 WAL per push; push acked only after S3 persistence; visibility via conditional PUT (CAS on ETag) to a per-repo WAL index → pushes linearizable; no elections, no routing table (rendezvous hashing); local NVMe repos are disposable caches rebuilt from WAL; replicas use conditional GET (<10 ms avg); only primary compacts. **120 pushes/s on S3 Standard, 300+ on S3 Express One Zone, linear read scaling to 100 replicas** (https://cursor.com/blog/git-at-any-scale).
- *Enroute* (Oct 13 2026, Rust, OSS): Raft-replicated per-repo "ledger" of refs + layer list; objects in buckets as per-commit "segments" (deltas only against same path in parent) so fetches don't walk trees; small pushes inlined in log, flushed ~1/s; claims **7,600 concurrent pushes/s** into one repo at ms latency; vs stock git 2.56 shallow clones >2× faster, full clones ~17% slower, incremental fetch ~13% slower; cold clone of linux.git 128.6 s vs warm 126.0 s (https://enroute.sh/blog/everyone-is-doing-git-on-s3-wrong).
- *Tigris objgit* (Sep 15 2026): re-made packfile format (`.bin` ≤128 MiB + fixed-width `.cue` index with compressed+uncompressed sizes, zstd, deltas as separate entries) so objects are fetched by HTTP Range; push requests 231→18, clone 323→17 (4–14× wall-time) (https://www.tigrisdata.com/blog/objgit-packfiles/).
- *Netlify*: S3 holds loose objects/packs natively and refs as JSON with `If-Match` ETag CAS; pods keep LRU local caches; per-repo write mutex; "multiple millions of new projects/month" (https://www.netlify.com/blog/how-we-built-git-storage-for-millions/).
- *gitgres* (Feb 2026): git ODB/refdb in Postgres via libgit2 backends — "a neat hack"; no delta compression (10 MB file × 100 edits ≈ 1 GB vs ~50 MB packed) (https://nesbitt.io/2026/02/26/git-in-postgres.html). "Nexus" as a git-on-object-storage project: UNVERIFIED (nothing found).

**Other hosts.** Sourcehut: plain bare repos on disk, Python/Go services, Postgres, email-centric (general knowledge; 2026 blog has no infra posts — https://sourcehut.org/blog/). Gitea/Forgejo: bare repos on local FS, shell out to `git` (go-git only behind a build tag), LFS/attachments optionally to S3 (general knowledge). Codeberg (June 2025 → May 2026): 3 bare-metal Debian servers, CephFS holds all Forgejo data (git, LFS, avatars), SSD tier added because HDD too slow for small-file git I/O, Galera multi-write DB, Redict Sentinel; now **1 read-write + 2 read-only Forgejo instances** with HAProxy routing unauthenticated GET/HEAD/OPTIONS to RO nodes; authenticated reads can't be balanced because page views write (notifications), and a hot-standby RW needs more Forgejo patches (https://blog.codeberg.org/letter-from-codeberg-we-love-our-new-infrastructure.html, https://codeberg.org/forgejo/discussions/issues/259). Google Piper/CitC: 2016 CACM paper (Potvin & Levenberg) — "tens of thousands of developers"; widely cited figures (86 TB, ~2B LOC, ~35M commits) are from that 2016 paper, not re-verified here (https://research.google/pubs/why-google-stores-billions-of-lines-of-code-in-a-single-repository/). Meta Mononoke: Rust server, OSS build supports MySQL/SQLite/file/S3, "still in development," omits Thrift APIs/MySQL failover/CacheLib; Sapling README lists Mononoke and EdenFS as "not yet supported publicly" (https://github.com/facebook/sapling/blob/main/eden/mononoke/README.md). Microsoft: VFS for Git README says "strongly recommend Scalar" for new deployments; Scalar shipped in Git 2.38 (Oct 2022): blobless partial clone by default, sparse-checkout, background maintenance (`gc.auto=0`, `fetch.unpackLimit=1` + multi-pack-index, changed-path Bloom filters) (https://github.com/microsoft/VFSForGit, https://git-scm.com/docs/scalar).

**Git core features a forge must exploit.** Geometric repacking + multi-pack-index bitmaps (GitHub 2021: repack 1 min→15 s avg, 5.67 CPU-days/hour saved; kernel traversal 33 s→1.57 s with bitmaps) (https://github.blog/engineering/scaling-monorepo-maintenance/). Git Merge 2026 (Elijah Newren, GitHub): experimental `pack-aggregate` turned 1,427 packs + 13,578 loose objects into 5 packs in 6.17 s (7,260 packs → 14 in 45 s); cross-pack lookups up to ~250× slower than single-pack; merge-base early-exit gave 70× on one monorepo, 20× average on another; `git backfill` makes `log -p` in partial clones need no extra fetches; shallow-clone pushes can resend GBs (fix on list). Git 2.56 (Sep 2026): `cat-file --batch-command remote-object-info`, `repack --drop-filtered` (3.1 MB → 156 KB demo), `git history drop`, `git refs create/delete/update/rename`. Schedule: **2.56 Sep 2026 → 2.98 Dec 2026 → 2.99 (LTS, last pre-Rust) + 3.0 Spring 2027**; 3.0 = SHA-256 default for new repos, reftable default, Rust mandatory (auto-detected 2.52, default-on 2.55) (https://about.gitlab.com/blog/whats-new-in-git-2-56-0/, gist above). Reftable: immutable sorted prefix-compressed tables, atomic `tables.list` swap, tombstones; deleting one packed ref in a multi-million-ref repo rewrote >2 GB at GitLab. Protocol v2 (ref-prefix filtering, since Git 2.18; default since 2.26 — general knowledge). Bundle URIs: supported by Gitaly (docs page exists; status/versions UNVERIFIED — page redirected to auth). Packfile URIs (`uploadpack.blobPackfileUri`) are used by Google's JGit hosting to offload blobs to CDN (general knowledge).

**SHA-256 status.** GitLab: experimental SHA-256 projects since Aug 19 2024 ("test projects only") (https://about.gitlab.com/blog/gitlab-now-supports-sha256-repositories/). GitHub: **private preview announced at Git Merge (Sep 17 2026)**, not GA; Google bridges SHA-256 sources into SHA-1 internally via Copybara; brian m. carlson is building server-side interop (SHA-256 canonical, SHA-1 view derived, never mixed in one graph); Scott Chacon (GitButler, Oct 1 2026) argues the default flip is "a costly mistake" (gist; https://blog.gitbutler.com/). gitoxide has hash abstraction + reftable crate in progress but lists Git 3.0 parity as unfinished (https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md).

**Large files.** Hugging Face Xet: content-defined chunking (~64 KB chunks, rolling hash; 64 MB blocks in a CAS per docs), global dedup, Rust client (`hf-xet`), Git LFS bridge returning a presigned URL for legacy clients. Migration: default for new users May 2025; **500k repos / 20 PB moved in ~6 months**; CAS peaked ~300 Gb/s; largest single user 6.1 PB/42k repos (https://huggingface.co/blog/migrating-the-hub-to-xet, https://huggingface.co/docs/hub/storage-backends). git-annex (symlink/pointer + many backends) and DVC (ML pipelines, remote storage) remain niche/general knowledge; LFS remains the interoperable protocol.

## 2. Monorepo scale

**What breaks GitHub (official limits).** `.git` on disk 10 GB; 3,000 entries/directory; depth 50; 5,000 branches; push ≤2 GB; object 100 MB hard (1 MB recommended); ≤15 reads/s and ≤6 pushes/min per repo recommended; PRs: 1,000 open against one branch, 1 merge/min, diff ≤20,000 lines or 1 MB, ≤300 files, 400 lines/20 KB auto-loaded per file, rebase-and-merge ≤100 commits; 100,000 repos/org (https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits). GitHub Enterprise Importer raised migration cap 20→40 GB in June 2025 citing monorepos (https://github.blog/changelog/2025-06-03-increasing-github-enterprise-importers-repository-size-limits/). Azure Repos 5 GB, Bitbucket Cloud 4 GB (vendor docs via search). CODEOWNERS must be <3 MB or it is silently ignored; last-match-wins (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

**How the giants host.** Chromium/Android: Gerrit + Google's JGit-based hosting (googlesource.com), Android via `repo` multi-repo manifests; Linux: git.kernel.org + lore.kernel.org public-inbox + `b4` (am/shazam/prep/send/trailers; `b4 review` TUI alpha) (https://b4.docs.kernel.org/en/latest/; hosting facts general knowledge). Mercurial at Git Merge 2026: flat manifests let a 26M-revision private repo fit in 26 GB vs ~2 TB tree-based (1.3%). Josh (proxy/filter) builds reversible sub-repo projections of a monorepo (~30 filter ops; incremental update 196 ms vs 4.59 s full filter-repo) — used by an automotive supplier and the Rust project (gist). Bazel/Buck2 remote caches (Remote Execution API; BuildBuddy, NativeLink) are general knowledge — a forge should host an RE-API-compatible CAS, not reinvent.

**Trend/requirements.** Cursor: enterprise repos "have become large monorepos that need many replicas for CI," while agents spawn huge numbers of tiny short-lived repos — both ends must be cheap. Forge must-haves: server-driven sparse-checkout profiles (Scalar semantics), path-scoped permissions and CODEOWNERS compiled server-side (not a 3 MB text file), path-filtered CI from a changed-paths index, partial-clone promisor serving, bundle/packfile URIs for clone offload, and pack maintenance that scales with new objects not repo size (geometric).

## 3. Code review engines

- **GitHub PR (branch-centric)** gained native **Stacked PRs (Apr 14 2026)** via `gh-stack`: stack map UI, per-layer diffs, merge whole stack through merge queue, auto-rebase of remaining PRs (https://www.infoworld.com/article/4158575/github-adds-stacked-prs-to-speed-complex-code-reviews.html). **Graphite joined Cursor (Dec 19 2025)**; "hundreds of thousands" of engineers; its forge ambition was shelved by the acquisition (https://graphite.com/blog/graphite-joins-cursor; gist). Graphite's Git Merge data: bot comments on PRs <1% pre-2023 → ~25% → high-30s%; open PRs per developer ~4 → 20+ — review's remaining value is change management and shared understanding, not validation.
- **Gerrit (change-centric)**: Change-Id trailer, patch sets, interdiff between any two patch sets, labels; 3.14 adds WebUI modernization, "Review Agent (AI chat)," Gerrit Flows; 3.15 on Java 25 (https://www.gerritcodereview.com/releases-readme.html). Gerrit design doc: read jj's **`change-id` commit header (32-char reverse-hex, standard agreed with GitButler)** so no commit-msg hook is needed; plain `git rebase`/cherry-pick still drops the header (https://www.gerritcodereview.com/design-docs/support-jujutsu-use-cases.html). jj: `jj gerrit upload` experimental since 0.34 (Oct 2025), more flags in 0.39 (Mar 2026) (https://docs.jj-vcs.dev/latest/gerrit/, changelog).
- **Phabricator/Phorge**: differential revisions with "diff of diffs" — Phabricator archived 2021, Phorge is the community fork (general knowledge).
- **GitButler**: Butler Review (commit-based, chat-centric, beta Mar 2025); 0.22 (Aug 2026) native GitHub stacked PRs; "Git Meta" (Scott Chacon, Git Merge 2026): metadata as commits under `refs/meta/`, SQLite local index, "CRDT-shaped" merge (strings LWW, sets union), 1M keys in ~80 s, PR-aware blame from imported GitHub data (https://blog.gitbutler.com/, gist).
- **Sapling ReviewStack**: stacked-PR UI over GitHub (general knowledge). **Tangled** demoed stacked PRs with range-diffs and interdiffs keyed on jj change IDs; issues/PRs stored as Git-backed collaborative objects (COBs) so maintainers keep them even if a contributor deletes PDS records (gist). **Radicle Patches**: COBs under `refs/cobs/` as commit DAGs, replayed topologically, CRDT-like union on sync; revisions carry base+head (https://radicle.dev/guides/protocol, 1.9.0 notes). **Pijul**: patch commutation, first-class conflicts, 1.0-beta; Nest hosting (https://pijul.org/).
- **Best-of-all-worlds model (synthesis):** the review unit is a *change* with a stable ID (jj header + Change-Id trailer compat), carrying ordered *patch sets*; UI shows per-patch-set diff, interdiff/`range-diff` between patch sets, and comments anchored to (change, patchset, blob, line-range) that migrate across rebases; stacks are first-class with per-layer approval and whole-stack merge-queue; review metadata stored in-repo refs (Git Meta/COB style) so it is portable and offline-readable; AI bot output confined to a separate lane (Graphite's 30%+ bot-comment figure says the signal/noise problem is real); email bridge (`b4`-compatible) for mailing-list projects.

## 4. Code search & intelligence

- **GitHub Blackbird** (Rust; Feb 2023 post): 45M repos, 115 TB raw, 15.5B documents → 28 TB unique after dedup/delta → 25 TB index; "sparse grams" (variable-length ngrams chosen by bigram weights) instead of trigrams; sharded by blob SHA; Kafka-driven ingest ~120k docs/s; full reindex 36 h (18 h with delta indexing); p99 per-shard ~100 ms; ~640 QPS per 64-core host (https://github.blog/engineering/infrastructure/the-technology-behind-githubs-new-code-search/). Note: dedup by blob SHA is why a forge must index *blobs* not files.
- **Zoekt** (Go, trigram + ctags symbol ranking; Sourcegraph-maintained since 2017) (https://github.com/sourcegraph/zoekt). Sourcegraph sizing: Zoekt index storage ≈ **50% of gitserver disk**; indexserver RAM ≈ 100 MB × CPUs × ~5; estimator caps at 50k users / 5M repos (https://sourcegraph.com/docs/self-hosted/deploy/scale, https://sourcegraph.com/docs/admin/deploy/resource_estimator). GitLab "exact code search" on Zoekt: enabled on GitLab.com since 16.6, beta (June 2025 blog), search API GA 18.4; GitLab plans to drop the Elasticsearch code-search backend as the rollout completes (https://about.gitlab.com/blog/exact-code-search-find-code-faster-across-repositories, https://gitlab.com/gitlab-org/gitlab/-/issues/554933). Hound/livegrep: single-node trigram/regex tools, fine to ~tens of GB (general knowledge).
- **Precise navigation**: GitHub **archived stack-graphs on Sep 9 2025** ("no longer supported") (https://github.com/github/stack-graphs). **SCIP** (protobuf successor to LSIF) has indexers for Java/Scala/Kotlin, TS/JS, Rust (rust-analyzer), C/C++, Ruby, Python, C#, Dart, PHP (https://github.com/sourcegraph/scip). Practical split: tree-sitter for syntax/symbol extraction at index time (cheap, incremental), SCIP uploads from CI for precise cross-repo nav, embeddings for semantic search as an add-on. Cost rule of thumb from the above: plan ~0.25–0.5× of source bytes for the trigram index (Blackbird ≈0.22× after dedup; Sourcegraph 0.5× of gitserver disk), and index per push incrementally from a commit-ordered event stream to get commit-level consistency.

## 5. Data layer & multi-tenancy

- **GitHub**: MySQL; 2019–21 "schema domains" (YAML) + query/transaction linters, then Vitess vertical partitioning with ms-scale write cutovers; 950k→1.2M QPS as load spread across clusters (https://github.blog/engineering/infrastructure/partitioning-githubs-relational-databases-scale/). Kafka for indexing events (Blackbird).
- **GitLab**: Postgres decomposed into **main, ci, sec**; cross-DB joins error since 14.3; "loose foreign keys" (async cleanup) replace cross-DB FKs (https://docs.gitlab.com/development/database/multiple_databases/). **Cells**: status "Experiment, GitLab.com only, Cells 1.0 in development"; epic 12383 says Cells 1.0 "mostly re-purposed to Protocells," internal customers only; routable-token HTTPS routing phase done June 2025 (https://docs.gitlab.com/administration/cells/, https://gitlab.com/groups/gitlab-org/-/epics/12383). **Geo**: Postgres streaming replication to read-only secondaries + tracking DB + log cursor; secondaries proxy writes to primary; manual promotion; same versions everywhere; "not an HA solution" (https://docs.gitlab.com/administration/geo/). **GHES HA**: one-way async replication (git, MySQL, Redis, Elasticsearch), manual failover, max 8 replicas incl. geo/cache (https://docs.github.com/en/enterprise-server@latest/admin/monitoring-and-managing-your-instance/configuring-high-availability/about-high-availability-configuration).
- **Single-binary/SQLite story**: Forgejo v14 (Jan 2026) added FK constraints (~5% of refs), fixed deadlocks, and "distributing read queries across multiple databases" (explicitly not HA); v14 also replaced Monaco with CodeMirror for the editor (https://forgejo.org/2026-01-release-v14-0/). Codeberg shows the ceiling: RO replicas only, no multi-writer. Litestream v0.5: LTX transaction-aware format, compaction → point-in-time restore, S3-conditional-write leases (no Consul), single replicator per DB; VFS read replicas "next" (https://litestream.io/, https://fly.io/blog/litestream-revamped/). River: transactional enqueue in the app's own transaction, **Postgres and SQLite**, Go/Ruby/Rust/TS clients; Pro adds workflows, global concurrency, sequences (https://riverqueue.com/). Oban (Elixir/Postgres), Temporal (durable workflows, separate cluster), Faktory (Redis-like server) are the alternatives (general knowledge). Caches: Redis/Valkey/Dragonfly interchangeable; Codeberg runs Redict Sentinel.
- **Resource usage**: GitLab CE documented 4 GB minimum (bundled Postgres/Redis/Sidekiq/Puma/Gitaly); Forgejo idle reports range 40–300 MB; no rigorous head-to-head exists (secondary blogs; treat as order-of-magnitude).

## 6. Security architecture

- **Sandboxing** (Sep 2026 comparison): Firecracker ~125 ms cold (tens of ms from snapshot), ~5 MB overhead, ~50k LoC Rust VMM; gVisor 200–600 ms, 18–50 MB, shares host kernel, syscall overhead "dramatic" on FS/network paths; Kata/QEMU 0.5–1 s, 50–130 MB, only path to confidential computing; Kata-on-Firecracker 125–625 ms but needs nydus snapshotter. 1,000 idle Firecracker VMs ≈ 5 GB vs 18–50 GB for gVisor on a 64 GB node; E2B grew 40k → 15M sandboxes/month (2024→2025) on Firecracker+Nomad with nested virt (https://bex.co/blog/2026/09/22/gvisor-vs-kata-vs-firecracker-agent-sandbox-isolation). GitHub-hosted runners: fresh Azure VM per job (except 1-CPU runners in containers on shared VMs); nested virt unsupported (https://docs.github.com/en/actions/using-github-hosted-runners/using-github-hosted-runners/about-github-hosted-runners). GitLab hosted runners: ephemeral GCE VM per job, Container-Optimized OS, 2–32 vCPU amd64/arm64, privileged DinD on SaaS tags (https://docs.gitlab.com/ci/runners/hosted_runners/linux/).
- **OIDC/keyless**: GitHub issuer `token.actions.githubusercontent.com`; `sub`/`repository`/`ref`/`environment`/`job_workflow_ref` claims; repos created after **July 15 2026** get an immutable ID-based subject format (https://docs.github.com/en/actions/concepts/security/openid-connect). Forgejo v15 (Apr 2026) added OIDC JWTs for Actions, ephemeral single-job runners, repo-scoped tokens; v16 added JWT "authorized integrations" and mirror SSRF hardening (https://forgejo.org/2026-04-release-v15-0/, https://forgejo.org/2026-07-release-v16-0/).
- **Supply chain**: GitHub artifact attestations = SLSA v1.0 Build L2 by default, **L3 when built in a reusable workflow**; public repos use Sigstore public-good log, private repos use GitHub's Sigstore instance without a transparency log (https://docs.github.com/en/actions/concepts/security/artifact-attestations). SLSA L3 requires isolation between runs and keeping signing material away from user build steps; v1.2 is current (https://slsa.dev/spec/v1.1/levels). Commit signing: gpg/ssh (`gpg.format=ssh`, Git 2.34+) and gitsign (Sigstore) — general knowledge.
- **Secrets**: GitHub push protection blocks at push/UI/API/MCP time, bypass requires a reason, every bypass → alert + audit + email; delegated bypass approvers (https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection). gitleaks/trufflehog are the OSS engines; OSV, Renovate, Dependabot for deps; Trivy/Grype for containers; Semgrep OSS engine LGPL with rules under a non-OSI license (general knowledge). **CodeQL CLI license** forbids CI/automated analysis of non-OSS code and non-GitHub-hosted OSS unless you are a GHAS customer, and forbids offering it as a hosted service — a new forge cannot bundle CodeQL (https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md).
- **Abuse history**: GitLab (May 17 2021) required a credit/debit card ($1 auth) for free shared-runner minutes after crypto-mining drove costs and outages; also quota-fail jobs, block namespace creation via API, put new public projects under minute quotas (July 2021) (https://about.gitlab.com/blog/2021/05/17/prevent-crypto-mining-abuse/). GitHub Actions and Heroku free tiers had the same 2021–22 problems (general knowledge).

## 7. Federation & decentralization

- **ForgeFed/Forgejo**: ForgeFed vocabulary covers repos, commits, patches, issues; Vervis is the reference impl; Forgejo "currently implementing"; Pagure plugin unmaintained (https://forgefed.org/). Forgejo federated stars existed as of 2025; a third-party test on 16.0.5 reports `POST /user/activitypub/follow` registered from 16.0.0 and returning 204 (UNVERIFIED officially). None of the v14/v15/v16/v17 release announcements (Jan/Apr/Jul/Oct 2026) mention federation; cross-instance issues/PRs remain unshipped (https://forgejo.org/2026-10-release-v17-0/).
- **Radicle** (1.10.3, Sep 8 2026; protocol vulnerability disclosed Sep 23 2026, transport section pulled pending fix): Ed25519 `did:key` node IDs, RID from initial identity doc, delegates + threshold canonical branch, gossip (node/inventory/refs announcements, signed+timestamped), Noise XK transport with git fetch multiplexed, per-peer `refs/namespaces/<NID>`, signed `refs/rad/sigrefs`, COBs for issues/patches; private repos = allow-listed replication, no encryption at rest (https://radicle.dev/guides/protocol, https://radicle.dev/).
- **Tangled/atproto** (€3.8M seed; Git Merge 2026 talk): PDS holds signed repo-declaration records; **knots** (headless Git remotes, per talk notes now Rust and not using the git binary server-side — earlier reports said sqlite + bare repos) hold repos, issues, PRs, ACLs as COBs projected into an AT repo (MST) for relay ingestion; **spindles** = CI; **Bobbin** = ~100 MB in-memory index hydrating in <30 s; knot demo on Cloudflare Workers; critics note repo data living outside the PDS breaks the "user data on PDS" norm (gist, https://blog.tangled.org/intro/).
- **git over nostr**: NIP-34 (draft): kinds 30617 repo announce, 30618 repo state, 1617 patch (<60 KB), 1618/1619 PR + update, 1621 issue, 1630–1633 status, `nostr://` clone via git-remote-nostr (https://github.com/nostr-protocol/nips/blob/master/34.md; gitworkshop.dev). git-ssb (Scuttlebutt, ~2016) is the historical precedent (general knowledge).
- **Email**: lore.kernel.org/public-inbox + `b4` + `lei` remain the kernel's "forge"; sourcehut's lists.sr.ht builds review on it (general knowledge; https://b4.docs.kernel.org/en/latest/).
- **Interop**: Gitea/Forgejo expose GitHub-compatible API subsets and Actions-compatible YAML (Forgejo v16 even accepts GitHub cron timezone syntax); `gh` targets GitHub/GHES only (UNVERIFIED for 2026). Cross-forge PRs are impractical today; the realistic bridge is (a) email patches both ways and (b) in-repo COB-style review data that any forge can import.
- **Identity portability**: did:key (Radicle), did:plc (atproto), WebAuthn passkeys (all major forges); nothing yet ties a passkey to a portable code-signing identity except Sigstore's OIDC-bound certs.

## 8. Implementation stack choices

- **Rust is winning the data plane**: Blackbird, Mononoke, Enroute, Tangled knots, GitButler (and its June 2026 "Grit: rewriting Git in Rust with agents" experiment), Radicle, gitoxide, objgit's server, Firecracker, Git itself (mandatory Rust in 3.0). **Go owns the control plane/app layer**: Gitea/Forgejo, Gitaly, Zoekt, Woodpecker, Dagger, River. Elixir/Phoenix LiveView gives cheap realtime but breaks the single-binary story (Burrito aside) and lacks git libraries (general knowledge).
- **gitoxide (gix 0.60.0, Oct 8 2026)**: clone/fetch incl. shallow, diff with rename tracking, status, blob/commit merge done; tree merge "needs a rewrite," push/receive-pack plumbing incomplete, rebase/cherry-pick orchestration missing, MIDX read/write, reftable crate in progress, SHA-256 prepared but Git 3.0 parity unfinished (https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md). Conclusion: gix for reads/diff/blame/graph, the `git` binary for receive-pack/merge/maintenance (Gitaly's choice; libgit2 is the least maintained path and was dropped by Gitaly — general knowledge).
- **UI for huge diffs**: GitHub's own thresholds (400 lines/20 KB auto-load per file, 300 files, 20k lines/PR) are the benchmark; Forgejo moved to CodeMirror 6 for performance/accessibility/mobile (Jan 2026). CodeMirror 6 + windowed rendering beats Monaco for read-mostly diff views (general knowledge).
- **CRDTs**: Loro 1.0 (Fugue text, movable tree/list, shallow snapshots, Rust/WASM/Swift); Automerge 3 (Jul 2025) cut memory >10× (Moby Dick 700 MB → 1.3 MB) by using the columnar format at runtime; Yjs remains the ecosystem default (https://github.com/loro-dev/loro, https://automerge.org/blog/automerge-3/).
- **Sync engines**: Zero (zero-cache Postgres replica + ZQL + custom mutators; $30/$300/$1,000+ tiers; 1.0 reported June 2026 by secondary sources) (https://zero.rocicorp.dev/); Electric (HTTP "shapes" through CDNs, claims 1M+ concurrent readers, **joining Neon at Databricks**) (https://electric.ax/); PowerSync (WAL→YAML sync rules, LWW) (secondary sources). Linear-style server-sequenced sync is the right fit for issue trackers; CRDTs only for shared text.
- **Benchmarks**: no credible Forgejo-vs-GitLab benchmark exists; the only hard numbers are vendor minimums (GitLab 4 GB) and anecdotes (Forgejo ~300 MB with a runner).

## Recommended architecture for a new forge in 2026

**Stack:** Rust monolith (Axum/Tokio) that ships as one static binary with embedded web assets and three runtime profiles selected by config, not forks: *solo* (SQLite + local FS + in-process queue + Docker/gVisor runner), *team* (Postgres + local NVMe + S3 + NATS JetStream + Firecracker), *cloud* (same, plus per-region cells and a thin global router). Git data plane: `gix` for reads, `git` subprocess for receive-pack/merge/maintenance, on a manifest-versioned object-storage layout with NVMe caches. Search: embedded Rust trigram/sparse-gram engine (or Zoekt sidecar in team/cloud) + tree-sitter + SCIP ingestion. UI: TypeScript (SvelteKit or React) with CodeMirror 6, SSE realtime, HTTP-shape sync for issues/PR metadata, Loro for collaborative text.

**Evidence-backed decisions (20):**
1. **Object storage is the source of truth; disks are caches.** Manifest/WAL + CAS publish (Cursor 120–300 pushes/s and 100 linear replicas; GitLab's 2026 design; Netlify) beats 3-replica 3PC (Spokes) in ops cost and elasticity. Solo profile uses the same code with a "filesystem object store."
2. **Per-repo manifest with CAS; readers pin a manifest (MVCC); ref conflicts resolved by 3-way manifest merge** — exactly GitLab's Git Merge 2026 design, upstream-compatible with pluggable ODB.
3. **Reftable from day one** — avoids GitLab's >2 GB packed-refs rewrite and matches the Git 3.0 default.
4. **Hash-agnostic object IDs (20/32 bytes everywhere), SHA-1 default, SHA-256 opt-in** — GitHub is only in private preview, GitLab is "test projects only," Git 3.0 flips the default for *new* repos in Spring 2027; be first to GA.
5. **Shell to `git` for writes/merges; gix for reads** — gix push and tree-merge are incomplete; Gitaly proves subprocess-git scales to GitLab.com.
6. **Geometric repack + MIDX bitmaps + commit-graph Bloom filters on a background scheduler; adopt pack-aggregate when upstreamed** — GitHub's 1 min→15 s repacks, 5.67 CPU-days/hour saved.
7. **Protocol v2 only; bundle-URI/packfile-URI served straight from object storage/CDN; promisor (blobless/treeless) serving; Scalar-style sparse profiles stored server-side** — the only way large monorepos clone fast without a VFS.
8. **Large files = CDC content-addressed store (Xet-style 64 KB chunks) with an LFS-protocol bridge** — HF migrated 20 PB this way; LFS stays the interoperability API.
9. **Exactly two SQL targets: SQLite (solo) and Postgres (team/cloud); no MySQL.** Forgejo's three-backend matrix and Codeberg's Galera story show the cost; Litestream v0.5 gives solo users PITR backups to S3.
10. **Tenancy key (`org_id`) on every row, schema domains + cross-domain query linter from commit one** — GitHub needed years to retrofit; GitLab's Cells program is still "Experiment" largely because of this.
11. **Jobs via transactional outbox in the primary DB (River model, Postgres and SQLite); NATS JetStream only for fan-out/indexing events in team/cloud; Redis/Valkey never authoritative** — Codeberg's read-only replicas hit exactly the "page view writes" problem that an outbox avoids.
12. **Search: index blobs not files, shard by blob SHA, drive from the commit-ordered event stream (commit-level consistency), budget ~0.25–0.5× source bytes** — Blackbird (115 TB→25 TB) and Sourcegraph (50% of gitserver disk). Tree-sitter symbols for ranking; SCIP uploads from CI; stack-graphs is archived, don't build on it.
13. **Review unit = change-id (jj commit header + Change-Id trailer compat), patch sets, interdiff/range-diff, first-class stacks, merge queue; review metadata mirrored into `refs/meta/` (Git Meta/COB style)** — GitHub shipped stacks in Apr 2026, Gerrit is adopting the jj header, Tangled demoed interdiffs on change IDs; in-repo metadata makes reviews portable and offline-readable.
14. **CI isolation: Firecracker microVM per job with snapshot restore (cloud), gVisor/Docker fallback (solo); ephemeral single-job runner credentials** — ~125 ms boot, ~5 MB overhead, strongest boundary; GitHub/GitLab both use VM-per-job; Forgejo v15 already does ephemeral runners.
15. **Built-in OIDC issuer with immutable ID-based `sub`, platform-held signing for SLSA L3 provenance via Sigstore, optional private transparency log** — mirrors GitHub's July 2026 subject change and attestations L3-via-reusable-workflow model.
16. **Pre-receive secret scanning with bypass-with-reason + audit (gitleaks-compatible rules); dependency scanning via OSV + Renovate; SAST via Semgrep OSS; container scanning via Trivy — never bundle CodeQL** (license forbids hosted/non-OSS use).
17. **Free CI requires card verification or a verified identity, hard CPU/minute quotas, and per-job egress policy** — GitLab's 2021 playbook; sandboxes don't solve egress/attribution.
18. **Multi-region = region-pinned orgs ("cells") with async replication for DR (Geo/GHES model), object-storage cross-region replication, and a stateless global router** — data residency falls out of pinning; don't attempt multi-writer SQL.
19. **Federation: ForgeFed outbound (stars/follows/issue comments) + email patch bridge (`b4`-compatible) + GitHub-REST-compatible API subset + COB export** — cross-forge PRs aren't practical in 2026; portability of review/issue data is.
20. **UI: CodeMirror 6 with windowed diff rendering and GitHub-like lazy thresholds (400 lines/20 KB per file); issues/PR lists via HTTP-shape sync with server-sequenced writes (Linear/Electric pattern); Loro CRDT only for shared PR descriptions/comments** — Forgejo dropped Monaco for performance; Automerge 3 / Loro 1.0 make CRDT text cheap, but LWW sync is enough for structured records.

**Trade-offs:** Rust slows initial feature velocity vs Go/TypeScript but is where every serious 2025–26 git-storage and search system landed; subprocess-git costs ~ms per op vs in-process gix but removes correctness risk; object-storage-authoritative adds S3 PUT latency to pushes (Cursor's cap) but makes replicas free; two SQL targets double migration testing; Firecracker needs bare-metal or nested-virt hosts (self-hosters get the gVisor fallback); in-repo review metadata inflates refs (mitigated by reftable + promisor pruning).
